- Clarified governance ownership
- Created reusable delivery patterns

Examples:

- GitHub versus SharePoint for developer content

- Standardization versus team autonomy
- Self-service versus ticket-driven processes
- Centralized standards versus federated ownership

## 7. Technologies and Practices

Show only technologies relevant to that initiative.

## 8. Lessons

Include two to four practical leadership or engineering observations.

This establishes credibility without turning the page into self-promotion.

# Featured Initiative Content

## Developer Platform & Tools

### Summary

Josh transitioned into leadership of Developer Platform & Tools to unify platform engineering, developer enablement, automation, and standards around a clearer platform ownership model.

### Problem

Developer workflows, delivery pipelines, engineering standards, onboarding, and supporting tools can become fragmented across teams. That increases cognitive load and makes the route from code to production harder to understand and maintain.

### Leadership Role

- Leads the Developer Platform & Tools organization
- Defines platform strategy and operating principles
- Guides platform product priorities
- Connects architecture, automation, developer tooling, and governance
- Creates visibility through team demonstrations and developer-facing content
- Promotes a build-once, enable-many model

### Approach

- Treat the platform as a product
- Develop reusable capabilities instead of one-off solutions
- Create approved golden paths
- Use automation to reduce manual processes
- Establish clear ownership and delivery practices
- Deliver in small increments
- Demonstrate work early and collect feedback
- Remain open by default where enterprise constraints allow

### Key Message

> The platform is not a single portal or tool. It is the connected system of workflows, standards, automation, and services that helps engineering teams move from idea to production.

## AIRIC

### Full Name

AI Reviewer for Infrastructure and Code

### Summary

AIRIC is an internal AI-assisted review capability designed to help engineers identify important areas in infrastructure and source-code changes while maintaining human accountability for review decisions.

### Problem

Large or complex changes can make it difficult for reviewers to quickly identify risk, defects, security concerns, and maintainability issues.

### Leadership Role

- Established and leads the initiative
- Guides architecture and security posture
- Evaluates models and deployment patterns
- Defines adoption and onboarding strategy
- Keeps human review central to the workflow
- Drives experimentation around review quality and false-positive reduction

### Approach

- Run inference within controlled enterprise boundaries
- Avoid unnecessary exposure of proprietary source code
- Integrate review into existing pull-request workflows
- Use AI to focus human attention rather than replace engineering judgment
- Evaluate grounding and cross-validation patterns
- Improve results through practical testing and iterative feedback

### Key Message

> AIRIC does not replace code review. It helps reviewers focus their attention where it is most valuable.

Avoid publishing internal infrastructure details, endpoints, credentials, or unsupported security claims.

## Developer Platform Portal

### Summary

A centralized entry point that helps engineers find onboarding guidance, approved delivery paths, standards, AI tooling, platform products, and support resources.

### Problem

Developer information is frequently distributed across repositories, SharePoint sites, service systems, team channels, and informal knowledge networks.

### Leadership Role

- Defined the portal vision
- Established the information architecture
- Built and demonstrated early implementations
- Connected the SharePoint and GitHub experiences
- Positioned low cognitive load and low friction as primary design requirements
- Led feedback and adoption discussions

### Approach

- Use SharePoint as the broadly accessible front door
- Use developer-friendly GitHub content where appropriate
- Organize around what an engineer is trying to accomplish
- Surface onboarding, golden paths, standards, AI tooling, and help
- Minimize access barriers and unnecessary context switching

### Key Message

## Local AI Developer Experience

### Summary

An enterprise-safe approach to AI-assisted software development using locally hosted language models and developer tools.

### Problem

Engineering teams want AI-assisted coding capabilities, but proprietary source code, cost, licensing, model suitability, and enterprise governance introduce constraints.

### Leadership Role

- Championed the local AI development model
- Evaluated tools and model options
- Established security and licensing considerations
- Worked with the team to test practical coding workflows
- Connected recommendations to responsible AI guidance
- Included the workflow in broader developer enablement

### Approach

- Keep model inference local where the use case requires it
- Prefer enterprise-approved models and licenses
- Integrate with familiar developer tools
- Test on real engineering tasks
- Document limitations instead of overselling model performance
- Give developers practical guidance rather than forcing them to independently evaluate the entire AI ecosystem

### Key Message

> AI tooling should improve the developer experience without requiring teams to compromise enterprise source-code protections.

## Cloud Governance Transformation

### Summary

Josh chairs a federated cloud governance effort focused on enabling secure, compliant, scalable cloud adoption through shared standards, clear ownership, and increasingly automated controls.

### Problem

Cloud governance can become fragmented across architecture, security, operations, financial management, data, and platform teams. Unclear ownership and disconnected standards create inconsistency and slow decisions.

### Leadership Role

- Chairs the Cloud Governance Committee
- Facilitates decisions across governance pillars
- Leads governance operating-model discussions
- Supports audit walkthroughs and corrective-action responses
- Helps establish review cadences and accountability models
- Promotes policy-as-code and platform automation
- Clarifies the boundary between governance and project execution

### Approach

- Use a federated governance model
- Establish shared standards and clear accountability
- Keep policies cloud-agnostic where practical
- Allow provider-specific implementations where necessary
- Review standards on a defined cadence and when significant changes occur
- Collect cross-pillar feedback
- Treat governance artifacts as living documents
- Encode standards into platforms and delivery workflows where practical
- Escalate exceptions without turning the committee into a project-delivery team

### Key Message

> Effective governance establishes clear boundaries and makes responsible delivery repeatable. It should not require a committee to execute every cloud project.
